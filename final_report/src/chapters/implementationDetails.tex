\section{Dataset Preparation and Refinement}

The foundational quality of a fine-tuned model is directly dependent on the cleanliness and relevance of the training data. For this project, we developed a specialized pipeline to transform general-purpose instruction datasets into a high-fidelity algorithmic training set by integrating automated LLM classification with manual verification.

\subsection{Alpaca Dataset Refinement}
The primary source for our instruction-following data was the \textbf{iamtarun/python\_code\_instructions\_18k\_alpaca} repository. To focus the model on logical reasoning and competitive programming (C.P.), we executed the following refinement process:

\begin{itemize}
    \item \textbf{Automated Classification:} We employed the \texttt{qwen2.5-coder:1.5b} model to evaluate the 18,000 raw rows. The model was tasked with identifying problems specifically involving algorithmic logic and competitive programming structures.
    \item \textbf{Filtering Results:} Approximately 12,000 problems were initially flagged as high-quality. Following this, a rigorous manual audit was conducted to prune misclassified entries (e.g., general scripting tasks or non-logic-heavy prompts).
    \item \textbf{Final Distribution:} After the removal of misclassified rows and duplicates, the final Alpaca-refined dataset consisted of \textbf{11,926 rows} of high-quality Python code paired with clear natural language descriptions.
\end{itemize}



\subsection{FlyTech Dataset Processing}
To supplement the algorithmic data with broader technical coding patterns, we utilized the \textbf{FlyTech} Python dataset. Given its large initial volume, a strict cleaning pipeline was necessary to ensure data integrity:

\begin{itemize}
    \item \textbf{Initial Filtration:} Out of an initial pool of \textbf{42,000 rows}, we implemented scripts to detect and remove exact and near-duplicate samples. Furthermore, any entries with null, missing, or empty problem descriptions were discarded to prevent the model from learning incomplete instructions.
    \item \textbf{Quality Control:} After the initial cleaning phase reduced the pool to 22,000 samples, we performed a secondary heuristic filter to identify the most educationally dense and logically sound snippets.
    \item \textbf{Final Selection:} This process resulted in a final selection of \textbf{9,616 high-quality samples}, ensuring that only the most robust examples contributed to the fine-tuning process.
\end{itemize}

\subsection{Data Filtering and Complexity Heuristics}
To ensure the fine-tuning process was not degraded by low-entropy or repetitive data, we implemented a custom \textbf{Complexity Filtering} layer. This programmatic filter targeted two primary noise factors: trivial, non-informative solutions and ``loop-hallucination'' patterns commonly observed in raw web-scraped datasets.

\subsubsection{Length-Based Thresholding}
Trivial code snippets, such as single-variable assignments or empty function definitions, fail to provide sufficient structural information for a 7B parameter model to capture complex logic. We applied a minimum word count threshold ($\tau_{min} = 7$) to ensure that every sample contained at least one functional block. The rationale for selecting seven tokens as the baseline is derived from the standard structure of a Python function. A minimal function definition (e.g., \texttt{def func(): return x}) typically comprises seven discrete tokens. By enforcing this limit, we ensured the model was forced to learn from logic-dense snippets rather than trivial examples that offer a weak learning signal. This strategy significantly reduced training loss by focusing gradient updates on meaningful algorithmic patterns rather than simple variable assignments.
\subsubsection{Lexical Diversity and Repetition Analysis}
One of the primary failure modes of Large Language Models (LLMs) is the generation of repetitive, circular code blocks. To prevent the model from inheriting these patterns during fine-tuning, we calculated a \textbf{Repetition Ratio} ($\rho$) for each candidate sample:
\begin{equation}
\rho = 1.0 - \left( \frac{|\text{Unique Tokens}|}{|\text{Total Tokens}|} \right)
\end{equation}

The selection of the optimal threshold was determined empirically. We evaluated the relationship between the repetition ratio and the resulting dataset size to balance data volume with quality, as summarized in Table \ref{tab:rep_ratio_exp}.

\subsubsection{Regex-Based Feature Isolation}
We utilized Regular Expressions (Regex) to programmatically identify and remove three primary types of non-functional text:
\begin{enumerate}
    \item \textbf{Single-Line Comments:} Identified via the pattern \texttt{\#.*?$\backslash$n}, ensuring that inline annotations are removed without disrupting the line-break structure.
    \item \textbf{Triple-Quote Docstrings:} Both double-quote (\texttt{"""..."""}) and single-quote (\texttt{'''...'''}) docstrings were targeted using the \texttt{DOTALL} flag to capture multi-line string literal documentation.
\end{enumerate}



The transformation process can be represented by the mapping function $f(C) \rightarrow C_{pure}$, where $C$ is the original source code. By removing these elements, we reduce the token count per sample while increasing the "logic density." This ensures that the attention mechanism of the Llama-2-7B model is focused strictly on variable transformations, control flow, and library calls.

\subsubsection{Impact on Training Efficiency}
Removing these components resulted in a more compact representation of the dataset. As shown in the training logs, models trained on "clean" code converged faster because the loss function was calculated solely on functionally relevant tokens. This step effectively reduced the noise-to-signal ratio, allowing the fine-tuned adapters to capture the nuances of Python's syntax more effectively.

\subsection{Train and test Split}
To ensure a robust evaluation of the fine-tuned model, we implemented a stratified train-test split. The dataset was partitioned into an 90\% training set and a 10\% test set, ensuring that the distribution of problem types and difficulty levels was preserved across both subsets. This stratification was crucial for evaluating the model's generalization capabilities, particularly on unseen problem types that may not have been adequately represented in the training data.

\subsection{Llama-2 Chat Template and Tokenization Mechanics}
To leverage the pre-trained conversational abilities of the Llama-2-7B-Chat model, all dataset samples were mapped to the specific Llama-2 Chat Template. This formatting is essential for the model to correctly identify the start and end of a user request versus the assistant's generation.



The structure utilized follows the schema:
\begin{verbatim}
<s>[INST] <<SYS>>
{system_prompt}
<</SYS>>

{user_instruction} [/INST] {code_solution} </s>
\end{verbatim}

We utilized the \texttt{LlamaTokenizer} with a fixed \texttt{max\_length} of 512 tokens. To handle variable-length inputs within a batch, we implemented right-side padding (\texttt{padding\_side="right"}). Crucially, the padding token was mapped to the \texttt{eos\_token} to ensure the model learns a clear termination signal for code blocks, preventing the common "infinite loop" generation failure mode.
\section{Hyperparameter Optimization}

The fine-tuning of Large Language Models (LLMs) is highly sensitive to the configuration of adapters and optimization schedules. To move beyond sub-optimal manual tuning, we implemented an automated Hyperparameter Optimization (HPO) pipeline using \textbf{Optuna} integrated with the \textbf{Hugging Face Trainer}.

\subsection{Bayesian Optimization via TPE}
Rather than utilizing a brute-force Grid Search or an uninformed Random Search, we employed the \textbf{Tree-structured Parzen Estimator (TPE)}. This Bayesian approach treats the optimization as a sequential process:
\begin{enumerate}
    \item \textbf{Exploration:} In initial trials (0--10), the sampler populates the search space.
    \item \textbf{Exploitation:} For subsequent trials, the TPE algorithm constructs a probability model of the hyperparameter performance, favoring regions that historically yielded a lower validation loss.
\end{enumerate}
Additionally, a \textbf{Median Pruner} was implemented to improve computational efficiency. This mechanism monitors the intermediate loss and terminates trials that are statistically unlikely to outperform the current "best" trial, saving significant GPU hours.

\subsection{Search Space Rationale}
The search space was carefully selected to address the specific constraints of the \texttt{Llama-2-7b} architecture and the coding dataset:

\begin{itemize}
    \item \textbf{Learning Rate ($\eta$):} We targeted a narrow log-space ($8 \times 10^{-6}$ to $3 \times 10^{-5}$). Given that we use 4-bit quantization, high learning rates can cause catastrophic forgetting or gradient explosion.
    \item \textbf{LoRA Configuration:} We varied the rank ($r$) and $\alpha$. While a higher $r$ (e.g., 32) allows for more complex parameter updates, our results indicated that a lower rank with a high $\alpha$ (scaling factor) provided better regularization for code generation tasks.
    \item \textbf{Scheduler Topology:} We compared \texttt{linear} decay against \texttt{cosine} and \texttt{cosine\_with\_restarts}. The \textit{cosine} scheduler proved superior as it maintains a higher learning rate for longer, allowing the model to escape local minima before gracefully decaying.
\end{itemize}

\subsection{Quantized Training Implementation}
To facilitate training on consumer-grade hardware while maintaining performance, we utilized \textbf{QLoRA (Quantized Low-Rank Adaptation)}. 
\begin{itemize}
    \item \textbf{4-bit NormalFloat (NF4):} This data type is information-theoretically optimal for normally distributed weights, which is typical in pre-trained LLMs.
    \item \textbf{Double Quantization:} We further quantized the quantization constants, saving an average of 0.37 bits per parameter.
    \item \textbf{Paged Optimizers:} To prevent Out-of-Memory (OOM) errors during spikes in sequence length, we utilized NVIDIA's unified memory to manage gradient buffers.
\end{itemize}

\subsection{Technical Rationale for Search Space Boundaries}
The search space for our Optuna trials was not arbitrary; it was constrained by the mechanics of \textbf{Low-Rank Adaptation (LoRA)}.
\begin{itemize}
\item \textbf{Rank ($r$) and Alpha ($\alpha$):} We tested ranks $\{8, 16, 32\}$. While higher ranks increase the degrees of freedom, they also increase the risk of overfitting on specific coding styles. We prioritized the scaling factor $\alpha = 4 \times r$, based on the observation that a larger alpha helps the model "assert" its new knowledge over the frozen base weights.
\item \textbf{The Dropout Factor:} We included a dropout range of $[0.05, 0.15]$. In code generation, dropout acts as a critical regularizer, preventing the model from memorizing specific variable names in the training set and instead forcing it to learn generalized Python syntax.
\end{itemize}



\subsection{SFT Loss Masking (Data Engineering)}
A critical component of our implementation was the custom tokenization logic. To ensure the model learned the logic of the code rather than the structure of the prompt, we applied \textbf{Instruction Masking}. During the calculation of the Cross-Entropy loss, all tokens corresponding to the user's "prompt" were assigned a label of $-100$. Consequently, the gradient updates were strictly driven by the "code" completion, focusing the model's capacity on generating syntactically correct and logically sound programming solutions.

\subsection{Formalism of Instruction Masking}In standard Supervised Fine-Tuning (SFT), the goal is to minimize the negative log-likelihood of the target sequence. However, in our implementation, we modified the objective function to focus strictly on code synthesis. Given a sequence of tokens $Y = \{y_1, y_2, \dots, y_n\}$, where $Y_{prompt} \subset Y$ and $Y_{code} \subset Y$, the loss $\mathcal{L}$ is calculated as:\begin{equation}\mathcal{L} = -\sum_{i \in Y_{code}} \log P(y_i | y_{<i})\end{equation}By assigning $y_i = -100$ for all $i \in Y_{prompt}$, the indices are ignored by the PyTorch \texttt{CrossEntropyLoss} function. This "Completion-only" training ensures that the model does not waste representational capacity on the user's input, which is already provided during inference. This is particularly important for Python generation, as the model must learn that the transition from the \texttt{[/INST]} tag to the \texttt{def} keyword is the most critical logical boundary.

\section{Final Fine-Tuning Implementation}

Following the identification of the optimal hyperparameter set through Bayesian optimization, the final fine-tuning phase was executed. This process utilized the \textbf{QLoRA (Quantized Low-Rank Adaptation)} methodology to adapt the \texttt{Llama-2-7b-chat-hf} model to the specialized domain of competitive programming and software engineering logic.

\subsection{Instruction Masking and Data Engineering}
A critical aspect of this implementation is the use of \textbf{Instruction Masking} (completion-only training). In standard causal language modeling, the model learns to predict every token in the sequence. However, for a coding assistant, learning to predict the user's prompt is redundant and can dilute the model's focus.

\begin{itemize}
    \item \textbf{Boundary Detection:} The \texttt{preprocess\_function\_with\_masking} identifies the precise token boundary between the user's \texttt{prompt} and the assistant's \texttt{code} completion.
    \item \textbf{Loss Suppression:} Using the PyTorch label masking logic, prompt tokens are assigned a value of $-100$. During the calculation of the Cross-Entropy loss, these indices are ignored by the functional objective.
    \item \textbf{Optimization Focus:} This mechanism ensures that the model’s gradient updates are purely driven by the syntactical and logical correctness of the generated code, forcing the model to allocate its entire representational capacity toward problem-solving rather than prompt reconstruction.
\end{itemize}



\subsection{Architectural Efficiency: QLoRA and NF4}
To facilitate high-performance tuning on limited hardware while maintaining 16-bit performance levels, we integrated \textbf{4-bit NormalFloat (NF4)} quantization.

\begin{itemize}
    \item \textbf{Quantization Strategy:} NF4 is information-theoretically optimal for normally distributed weights. By utilizing \textit{Double Quantization}, we further reduced the memory footprint by quantizing the quantization constants themselves.
    \item \textbf{Comprehensive Adaptation:} Based on the HPO results, LoRA adapters were not restricted to the attention heads (\texttt{q\_proj}, \texttt{v\_proj}). Instead, adapters were applied to all linear layers, including the MLP blocks (\texttt{gate\_proj}, \texttt{up\_proj}, \texttt{down\_proj}). This allows the model to capture deeper structural patterns inherent in complex programming languages.
\end{itemize}



\subsection{Optimization and Training Dynamics}
The final training utilized a \textbf{Cosine Learning Rate Scheduler}, which provides a smooth decay following an initial warmup period.

\begin{itemize}
    \item \textbf{Warmup Strategy:} A warmup ratio of approximately $6.93\%$ was implemented. This allows the model to stabilize its 4-bit weights and adapter gradients before reaching the peak learning rate of $2.91 \times 10^{-5}$.
    \item \textbf{Effective Batch Size:} To ensure stable gradient descent, we utilized a per-device batch size of 4 with \textbf{Gradient Accumulation} set to 4. This results in an effective batch size of 16, providing a smoother loss landscape and more reliable convergence.
    \item \textbf{Memory Management:} We employed \texttt{paged\_adamw\_32bit} and \textit{Gradient Checkpointing}. These features offload optimizer states to the CPU during VRAM spikes and re-compute the forward pass during backpropagation, respectively, enabling a maximum sequence length of 512 tokens without OOM errors.
\end{itemize}

\section{Evaluation}
The evaluation of the fine-tuned \texttt{Llama-2-7b} model was conducted through a multi-layered software ecosystem designed to ensure reproducibility, rigorous performance tracking, and granular analysis of the model's code generation capabilities.

\subsection{Software Infrastructure and Integration}
The evaluation framework leveraged several state-of-the-art software tools that provided a unified pipeline from trial analysis to final model validation:

\begin{itemize}
    \item \textbf{Weights \& Biases (W\&B):} This platform served as the primary telemetry suite. By initializing \texttt{wandb} within the \texttt{TrainingArguments}, we achieved real-time visualization of training dynamics. This enabled us to monitor the \textit{Validation Loss} and \textit{Gradient Norms} across 50-step intervals, ensuring that the model did not suffer from gradient instability despite the aggressive 4-bit quantization.
    
    \item \textbf{Hugging Face Hub API:} We utilized the \texttt{huggingface\_hub} library to maintain a robust versioning system. Every optimized checkpoint was synchronized to a private repository (\texttt{pradip777/llama-2-PCG}). This software integration allowed for "check-pointed evaluation," where intermediate model states could be loaded and tested against the final converged weights.
    
    \item \textbf{PEFT and BitsAndBytes:} The \texttt{peft} library was instrumental in evaluating inference efficiency. By loading only the 160MB adapter file onto the frozen 4-bit base model, we verified that the software could perform low-latency evaluation on single-GPU environments while maintaining the logical integrity of the \texttt{NF4} weights.
\end{itemize}

\subsection{Standardized Benchmarking: OpenAI HumanEval}
To objectively measure the coding proficiency of the fine-tuned model, we utilized the \textbf{OpenAI HumanEval} dataset. This dataset consists of 164 hand-written programming problems designed to test logic, algorithms, and language comprehension.

\subsubsection{The Pass@k Metric}
Code generation is inherently stochastic; therefore, simple accuracy is insufficient. We implemented the \textbf{Pass@k} metric, which measures the probability that at least one of the $k$ generated code samples passes the unit tests for a given problem. 



The software computes this using the unbiased estimator:
$$ \text{pass@k} = \mathbb{E} \left[ 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}} \right] $$
where $n$ is the total number of samples generated per problem (set to $n=5$ in our implementation), and $c$ is the number of samples that successfully passed the unit tests.

\subsubsection{Comparative Results}
We executed identical evaluation scripts for both the \textbf{Base Llama-2-7b-chat} and our \textbf{Fine-tuned LoRA Adapter}. The results demonstrate a significant uplift in technical proficiency after the instruction-masked fine-tuning process.


\subsection{Qualitative Assessment and Code Extraction}
Beyond numerical scores, we implemented a specialized inference and extraction pipeline (\texttt{evaluation.py}) to evaluate the practical usability of the model outputs.

\begin{itemize}
    \item \textbf{Regex-Based Extraction:} Because LLMs often wrap code in conversational "chatter," we developed a \texttt{re}-based extraction utility. This software identifies code blocks between triple backticks (\texttt{```python ... ```}) and falls back to keyword-based detection (\texttt{def}, \texttt{class}, \texttt{import}) to ensure a clean executable string is retrieved for the \texttt{check\_correctness} function.
    
    \item \textbf{Diversity via Stochastic Sampling:} During the generation of the 5 samples for HumanEval, we utilized a \texttt{temperature} of $0.8$ and \textit{Nucleus Sampling} (\texttt{top\_p=0.95}). This software configuration encouraged the model to explore different algorithmic paths, which is critical for achieving higher Pass@k scores compared to greedy decoding.
\end{itemize}

\subsection{Sampling Strategies for HumanEval}
The performance on the HumanEval benchmark is heavily dependent on the decoding strategy. We implemented a \textbf{Stochastic Decoding} pipeline to maximize the \textit{Pass@k} scores.
\begin{itemize}
\item \textbf{Temperature Scaling ($T=0.8$):} This softens the probability distribution, allowing the model to generate diverse algorithmic solutions across its five attempts per problem.
\item \textbf{Top-p (Nucleus) Sampling ($p=0.95$):} This restricts the model's vocabulary to the smallest set of tokens whose cumulative probability exceeds 0.95. This prevents "long-tail" hallucinations (random characters) while maintaining enough creativity to solve complex logical puzzles.
\end{itemize}

\subsection{Instruction Masking Strategy}
To ensure the model learns to generate code rather than simply repeating the prompt, we applied a custom tokenization strategy. During the preparation of the training tensors, we set the \texttt{labels} for all tokens belonging to the "Instruction" and "System" prompts to $-100$. This signals the loss function to ignore these tokens, forcing the model's weights to update based solely on the accuracy of the generated "Response" tokens.
